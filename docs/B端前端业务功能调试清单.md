# MiniPay 商户端 / 运营管理端业务功能调试清单

> 基准：`su` 分支，2026-08-07 14:00 之后的代码与当前工作区。调试时在“结果”列填写：`通过 / 不通过 / 与需求不符 / 暂未实现`，失败时记录请求标识 `requestId`。

## 1. 先确认系统边界

| 层 | 负责内容 | 不应负责 |
| --- | --- | --- |
| `merchant-web` | 商家账号登录、多商户切换、商户经营配置、订单与个人钱包展示 | 直接保存 Token、直接访问数据库、运营审核 |
| `ops-web` | 平台管理员登录、商户/应用审核与管理、全平台订单和通知查询 | 商户经营操作、资金记账、在后端内嵌 HTML |
| `management-bff` | 两套独立 Web 会话、CSRF、OAuth、接口代理和权限校验 | 保存支付/商户业务真相 |
| `identity-service` | 管理员和商家身份、验证码、密码、登录审计、OAuth | 托管 React/HTML/CSS/JS 前端资源 |
| `payment-service` | 商户、应用、支付、退款、转账、通知及运营查询 | 修改钱包余额 |
| `wallet-service` | 余额、冻结额、账单、TCC 资金动作 | 修改支付单或商户资料 |

统一前端技术栈：React 18 + TypeScript 5.8 + Umi Max 4 + Ant Design 6 + React Query 5 + Less；金额接口单位统一为“分”，页面显示为“元”；数据库状态保存英文枚举，页面显示中文。

## 6. 必测业务闭环

1. 商户提交入驻申请 → 运营要求补充 → 商户重提 → 运营通过 → 出现 ACTIVE 商户。
2. 商户初始化 → 默认应用/经营码各一份 → 领取密钥 → 配置回调 → 启用应用。
3. 商户开放 API HMAC 建单 → C 端支付 → 店主个人钱包入账 → 商户看板/订单与运营支付订单同时出现。
4. 商户订单发起全额退款 → 付款人回款、店主钱包扣回 → 商户和运营退款页状态一致。
5. 回调模拟 500/超时 → 自动重试 → 运营查看详情 → 人工重试 → 次数不清零且最终状态收敛。
6. 创建站内转账 → Wallet TCC 两侧账单完成 → 运营转账详情与付款/收款方账单一致。

## 7. 当前已识别的代码问题

| 问题 | 处理/结论 |
| --- | --- |
| 身份服务中混入完整 ops-web 构建产物 | 本轮清除；后端只保留登录和 OAuth 接口 |
| 管理端登录同时使用 BFF CSRF 和 Identity CSRF | 本轮拆分为 `/api/v1/csrf` 与 `/identity/api/v1/csrf` |
| `merchant-operations.tsx` 调用不存在的 `/api/v1/ops-gateway/**`，且没有路由 | 本轮删除旧页面及旧 service，现行统一使用 `/api/v1/ops/**` |
| 新增支付/退款/转账页面只有查询和详情 | 这是正确边界：运营端不应手工修改资金订单状态 |
| 新增订单与通知接口未写入 `contracts/openapi/ops-api-v1.yaml` | 后端 Controller 已实现、前端已调用，但缺少契约定义；在补齐 OpenAPI 和相应契约测试前，不应视为可稳定对外联调 |
| 商户页面大量功能集中在单个 `portal.tsx` | 功能可用但维护成本高；后续应按页面拆组件，不应在本次业务验收前大改行为 |
| 服务器配置把 `OPS_WEB_PUBLIC_URL` 与商户站点配成同一根地址 | 上线前必须给 ops-web 独立域名或独立路径，并由网关把该站点的 `/identity/*` 转发到 Identity；本地 8000/8001 已天然隔离 |
